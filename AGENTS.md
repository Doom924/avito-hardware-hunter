# Правила разработки и версионирования проекта

## 1. Схема версионирования (`MAJOR.MINOR.PATCH`)
- **Первая цифра (`X.0.0`)** — только **глобальные изменения** (новая архитектура, крупные модули, выход в новый этап развития). Только при её смене оформляется крупный переход и новый релиз.
- **Вторая цифра (`X.Y.0`)** — **небольшие и средние улучшения** (новые фильтры, колонки, удобство UI без смены архитектуры).
- **Третья цифра (`X.Y.Z`)** — **багфиксинг** (исправление ошибок, опечаток, утечек, стабильность).

## 2. Правила коммитов (`git commit`)
- Каждый коммит **обязательно** сопровождается подробным описанием того, что именно проделано:
  - Первая строка: краткая суть (`feat:`, `fix:`, `refactor:`, `docs:`).
  - Тело коммита (через пустую строку): маркированный список `- ...` всех внесённых изменений.
- При изменении функционала или исправлении багов обновлять `CHANGELOG.md`.

## 3. Технические инварианты проекта
- Не использовать `CTkScrollableFrame` (использовать `SmoothScrollFrame`).
- Все пути (`settings.json`, `hunter_history.db`, `browser_profile`) привязывать к `_app_dir()` для корректной работы `.exe`.
- Соблюдать потокобезопасность `HunterDB` (короткие соединения в `try/finally`).
